# 项目概览

> 状态：Phase 0.2c（协议、身份、Request/Offer 本机流程）· 最后更新 2026-11-07

## 1. 一句话

PeerServe（信约阁）是一个**无中心业务服务器**的 P2P 需求公告板：用户用自己的密钥发布需求、响应需求、签署协议，并各自保存可验证的事实记录与主观评价。

"阁"只是文化象征。**本项目不存在任何中心化的"楼阁服务器"**：所有契约数据分散存储在每一位用户的手机本地。

## 2. 要解决的问题

今天"附近的小协作"（打车、顺路带物、跑腿代购）几乎都经过平台：

- 平台控制入口、匹配规则与数据；
- 抽佣与规则不透明；
- 用户的历史记录留在平台，换平台即清零；
- 平台的"信用分"是平台资产，不是用户资产。

PeerServe 的假设是：**协作本身不需要一个中介持有数据**。把身份、协议、事件与评价都做成用户自己签名的可验证数据，让两个陌生人之间的约定变得可携带、可核验、可迁移。

## 3. 首批场景

| 场景 | Request 的关键字段 |
| --- | --- |
| 网约车 / 顺风车 | 起点、终点、时间窗、议价 |
| 快递 / 顺路带物 | 取件点、收件点、时限、收件人确认 |
| 外卖 / 代购 / 跑腿 | 商品清单、任务分工（下单者/传递者/收货者） |
| 其他本地服务 | 自由描述 + 时间 + 价格 |

三类场景共用同一套 `Request / Offer / Agreement / Event / Review` 模型，不写成三套系统。

## 4. 核心原则

1. **无中心业务服务器**——不依赖开发者运营的服务器保存任务主数据、控制交易或决定谁能参与。
2. **手机即节点**——每台设备都能创建、签名、保存、传播数据。
3. **用户拥有数据**——私钥与完整记录在用户设备，可导出、可迁移。
4. **开放协议**——任何人均可写客户端；格式公开、有版本号。
5. **不发币**——不要求加密货币、代币或链上手续费。
6. **事实与观点分离**——系统记录可验证事件；评价明确标为意见。
7. **不强制仲裁**——提供协商、证据保存与事实展示，不把投诉当事实。
8. **AI 只是工具**——AI 不控制身份、订单、信用或权限。
9. **第三方服务可替换**——支付、地图由用户选择的外部服务完成。
10. **渐进开发**——先验证两台设备之间的流程，再扩展发现与转发。

## 5. 非目标（MVP）

- 复制完整的美团 / 滴滴 / 快递企业系统；
- 自建支付、地图、导航、短信、实名验证；
- 发行代币、积分币、NFT 或投机机制；
- 统一的信用分、自动封禁或惩罚系统；
- 承诺消除诈骗、违约或现实风险；
- 让 AI 做最终裁判；
- 自研公链或自创密码学；
- 首版实现商用级跨平台 P2P 网络。

## 6. 与"区块链项目"的区别

| 常见做法 | PeerServe |
| --- | --- |
| 把订单哈希上链当作"存证" | 不引入链；签名事件本身即可自证 |
| 代币激励节点转发 | 不做激励层，转发是可选行为 |
| 全局公开账本 | 交易内容只在参与者之间交换 |
| 链上信用 | 事实统计与评价由客户端按本地数据计算并展示来源 |

原因见 [DECISIONS.md](DECISIONS.md) ADR-001、ADR-007。

## 7. 当前状态（诚实版）

**已具备**：Flutter 应用外壳、主题、精简首页、个人中心、内存身份页、需求公告板与发布表单、示例需求、需求响应（Offer）、widget 测试、CI；`osn_protocol`（无浮点 JCS、严格 JSON、信封、Request v1、Offer v1）与 `osn_identity`（Ed25519、did:key、验签）；RFC 8032 / JCS / 固定信封/Request/Offer 测试向量。

**不具备**：Offer/Agreement/Event/Review 业务对象、数据库、网络传输、发现、完整 UI 业务流程。

因此当前版本**不能**完成一次真实交易；身份与需求都只在内存中，重启即丢失。下一步见 [ROADMAP.md](ROADMAP.md)。
