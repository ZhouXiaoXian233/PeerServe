## 2. 关键流程：一次完整交易

```text
A: 发布需求 ──签名──▶ 公告
B: 浏览 ──▶ 详情 ──▶ 发 Offer（签名）
A: 查看 Offer ──▶ 接受 ──▶ 生成 Agreement（条款）
A、B: 各自查看同一份条款 ──▶ 各自签名 ──▶ 双方签名齐全 → "已达成"
B: 记录"开始服务"
B: 声明"已完成"        → 显示为「B 声称已完成」
A: 确认完成            → 显示为「A 确认已完成」，双方均签 → 「双方已确认完成」
A、B: 各自评价对方      → 显示为「评价（主观意见）」
```

## 3. 状态展示规则（不可违背）

| 事实 | 允许的文案 | 禁止的文案 |
| --- | --- | --- |
| 只有一方签了 Agreement | "等待对方签署" | "已达成协议" |
| 一方 `completion.claimed` | "B 声称已完成" | "已完成" |
| 双方 `completion.confirmed` | "双方已确认完成" | "已验证真实送达" |
| 存在 `dispute.statement_added` | "有争议陈述（1 条）" | "违规"、"诈骗" |
| 评价 | "评价（3 条，均为交易参与者）" | "信用分 4.2" |
| 数据来自缓存 | "来自节点 X · 5 分钟前收到" | （不标注来源） |
| 公告已过期 | "已过期，不可响应" | （继续显示为可响应） |

## 4. 视觉与交互原则

- 三类信息用不同视觉层级：**事实（签名/事件）** > **单方声明** > **主观评价**。
- 重要且不可逆的操作（发布、签署、撤回、导出身份）必须二次确认。
- 错误提示给出可执行建议，不泄露密钥、位置或对方隐私。
- 离线可用：本地数据始终可读，但顶部显示"数据可能过期 / 最后同步时间"。
- 不展示精确坐标给非参与者；参与者也要显式操作才展开。

## 5. 空状态与边缘情况

| 情况 | 表现 |
| --- | --- |
| 无身份 | 引导创建或导入，不允许发布 |
| 无网络 | 可浏览本地缓存与已参与交易，发布进入待发送队列（Phase 4） |
| 公告被撤回 | 详情页顶部标记"发布者已撤回"，不可新建 Offer |
| Offer 未被选中 | 标记"未选中"，不评价对方（未成交不允许评价） |
| 签名验证失败 | 醒目错误条 + "不要基于此内容交易"，提供删除/导出诊断 |
| 冲突事件 | 时间线并列显示两条，标"冲突：双方记录了不同的完成时间" |

## 6. 无障碍与本地化

- 文案先中文，关键词保留英文（`Request/Offer/Agreement`）便于对照协议文档。
- 目标：支持系统字体缩放、TalkBack、深浅色主题。
- 时间与金额使用 `intl` 格式化；协议层始终存 UTC 整数/字符串。
