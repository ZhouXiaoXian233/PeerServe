## ADR-001 首版不发币

- **状态**：已采纳（2026-10）
- **背景**：P2P 项目常以代币激励节点与早期用户，但这会引入投机、合规与"币价绑架产品"的风险。
- **选项**：(a) 发行代币激励转发/评价；(b) 积分制；(c) 完全不发币。
- **决定**：不发行代币、积分币或 NFT，不设链上手续费。
- **理由**：本项目的价值在于"两个陌生人可以自己完成约定并各自留证"，与激励层无关；引入代币会让"谁在维护规则"重新中心化（基金会/做市商）。
- **代价**：没有经济激励，节点转发与托管缓存难以自发形成；发现与可用性依赖用户善意与自建基础设施。
- **复审条件**：如果未来确有独立于代币的长期运维资金来源方案，可重新讨论，但必须单独 ADR 并明确"不使用代币"的替代路径。

## ADR-002 不做强制全局信用分

- **状态**：已采纳
- **背景**：平台式信用分（一个数字决定谁能交易）是最容易被滥用的中心化权力。
- **选项**：(a) 全局信用分；(b) 仅展示原始事实与评价；(c) 本地可配置的信任策略。
- **决定**：MVP 只做 (b)+少量 (c)：展示事实统计与评价原文、来源、签名状态；客户端可本地屏蔽身份；**不计算**跨身份的统一分数。
- **理由**：一条差评可能来自串通、误会或恶意；样本量与来源必须与结论一起呈现，否则等于系统背书一个未必成立的判断。
- **代价**：用户需要自己判断可信度，认知负担更高；难以一眼筛选陌生人。
- **复审条件**：若出现经过同行评审、可解释且不产生中心化权力的聚合方案，可作为**可选视图**重新评估，仍不得成为强制门槛。

## ADR-003 事实记录与用户评价分离

- **状态**：已采纳
- **背景**：把"双方签署完成确认"与"我觉得他不好"混在同一个分数里，等于让意见污染事实。
- **选项**：(a) 统一展示为评分；(b) 分开展示，事实在前、评价在后。
- **决定**：(b)。事实类：有效双方签署协议数、双方完成确认数、单方完成声明数、争议陈述数，均标注签名验证状态。评价类：评分分布、条数、是否来自交易参与者、签名是否有效。
- **理由**：签名能证明"谁签署了什么"，不能证明"服务好不好"；只有把两者分开，用户才能自己判断证据的分量。
- **代价**：界面更复杂，需要解释"事实 / 单方声明 / 意见"三种状态。
- **复审条件**：无需复审，这是项目的价值底线。

## ADR-004 Android 优先

- **状态**：已采纳
- **背景**：目标用户主要在移动端；iOS 需要付费开发者账号与 Mac 构建环境。
- **选项**：(a) Android 优先；(b) 双端同时；(c) 先桌面。
- **决定**：先 Android。Flutter 保留跨端能力，但 MVP 只验收 Android。
- **理由**：P2P 的真实约束（后台限制、蓝牙/mDNS 权限、电量）在 Android 上最典型，也最容易用真机验证。
- **代价**：iOS 用户暂时被排除；部分 API 后续需要适配。
- **复审条件**：Phase 3 之后，若 Android 流程稳定且有 iOS 维护者加入，再评估。

## ADR-005 先本地核心，再 P2P

- **状态**：已采纳
- **背景**：分布式网络调试成本极高；若业务核心与网络同时开发，失败原因难以归因。
- **选项**：(a) 先做网络再做业务；(b) 先做本地可验证核心，再用 `InMemoryTransport` 模拟，最后接真实传输。
- **决定**：(b)。Phase 1 完全不联网即可完成"发布→响应→签署→追加事件→评价"。
- **理由**：签名、规范化、状态投影的正确性可以纯单元测试验证；网络层只需保证"消息送达且不篡改"，从而把问题域切开。
- **代价**：早期 demo 看不到"两台手机互通"的效果；需要额外维护模拟传输。
- **复审条件**：无需复审。

## ADR-006 不自研密码学

- **状态**：已采纳
- **背景**：自研密码学是这类项目最常见的事故来源。
- **选项**：(a) 自研 Ed25519/JCS；(b) 使用成熟库（`cryptography` 等）并跑官方测试向量。
- **决定**：(b)。签名用 Ed25519；规范化用 RFC 8785 JCS；密钥派生与备份加密用标准原语（HKDF / AES-GCM / Argon2id）。
- **理由**：密码学正确性只能靠审计与向量，不靠"看起来对"。
- **代价**：受第三方库维护状态影响（见 [DEPENDENCIES.md](DEPENDENCIES.md)）；必要时需 fork 并接管维护。
- **复审条件**：当依赖停止维护或出现未修复漏洞时重新评估替代实现。

## ADR-007 不把订单内容与位置默认写入区块链

- **状态**：已采纳
- **背景**：链上存证常被当作"可信"的捷径，但不可篡改与隐私、删除权直接冲突。
- **选项**：(a) 订单哈希上链；(b) 完全不上链；(c) 仅可选的最小承诺（未来）。
- **决定**：MVP 选 (b)。未来若要 (c)，只允许最小化哈希/承诺，且必须先做隐私、费用、可用性与监管评估。
- **理由**：签名事件已经能证明"谁签署了什么"；上链不会让现实履约变得可验证，只会让位置与交易细节永久公开。
- **代价**：没有第三方时间戳锚定，无法向外部证明"某事件早于某时刻存在"。
- **复审条件**：出现真实的第三方争议场景且 (c) 的隐私影响可接受时再评估。

## ADR-008 P2P 发现的基础设施依赖

- **状态**：提案（待 Phase 2 技术验证）
- **背景**：手机之间直连需要发现与 NAT 穿透；任何 DHT/relay/信令都是"外部基础设施"。
- **选项**：见 [RESEARCH_OPEN_SOURCE.md](RESEARCH_OPEN_SOURCE.md) §3（`dart_libp2p` / `nearby` / `iroh` / WebRTC / Nostr relay / 裸 TCP）。
- **暂定决定**：抽象 `Transport` 接口；Phase 2 首选 `dart_libp2p`（Noise + Yamux + TCP + mDNS），用二维码交换 multiaddr 手动配对；relay/bootstrap 必须可配置、可替换、可关闭。
- **理由**：接口先行可以把"选错库"的代价限制在一个适配器内；手动配对把公网发现的风险推迟到 Phase 4。
- **代价**：手动扫码的首次体验差；libp2p 生态年轻，需锁版本与契约测试。
- **复审条件**：Phase 2 结束时，若单机/双机验证不达标（连接成功率、重连、后台行为），改用 `nearby`（局域网/BLE）或 `iroh`。

## ADR-009 签名规范化：JCS + 禁浮点 + 域分离

- **状态**：已采纳（Phase 0.2 实施）
- **背景**：JSON 序列化在不同语言/实现下不稳定（键顺序、数字格式、Unicode 转义），直接对"序列化结果"签名会导致跨端验签失败。
- **选项**：(a) 直接签 JSON 字符串；(b) 自定义二进制编码；(c) RFC 8785 JCS + 协议层禁浮点 + 域分离前缀。
- **决定**：(c)。签名字节 = `UTF-8("PeerServe:v1:" + JCS(payload))`；payload 中只允许 string/bool/null/int/array/object。
- **理由**：JCS 有跨语言测试语料；禁浮点绕开 JCS 最危险的部分（ECMAScript 数字格式）；域分离防止签名被其他协议重放。
- **代价**：金额必须用最小单位整数、经纬度用 1e-7 整数；模型层需额外约束。
- **复审条件**：若 JCS 实现被证明不可靠，可改为"自定义确定性编码 + 版本号"，但必须提供测试向量与迁移说明。

## ADR-010 私钥备份与丢失处理

- **状态**：提案（Phase 1 实施）
- **背景**：无中心服务器意味着**没有找回**；但"丢了就没了"需要用户事先明确知情。
- **选项**：(a) 服务端托管恢复；(b) 加密备份文件 + 用户口令；(c) 助记词。
- **决定**：MVP 用 (b)：私钥用 AES-GCM 加密导出，口令经 Argon2id 派生；不做云同步；不做助记词（避免用户把助记词当"账户密码"到处粘贴）。
- **理由**：(a) 违背无中心原则；(c) 对移动端用户易泄露。加密文件可放用户自选的云盘。
- **代价**：口令忘记即永久丢失身份；导出文件本身是攻击目标。
- **复审条件**：Phase 3 用户测试后评估是否需要助记词或多设备迁移方案。

## ADR-011 Phase 0.1 采用单包结构，pub workspace 延后

- **状态**：已采纳；Phase 0.2 已执行迁移（2026-11-07）
- **背景**：调研建议最终用 Dart pub workspaces 管理 `app/mobile` + `packages/osn_*`。但 Phase 0.1 只有应用本身，若同时建立 workspace 根与多个空包，会产生"看起来实现了"的误导，并增加冒烟测试之外的维护面。
- **选项**：(a) 立刻建立 workspace 根 + 5 个空包；(b) 只建 `app/mobile`，第一个真实包出现时再引入 workspace。
- **决定**：(b)。当 Phase 0.2 创建 `packages/osn_protocol` 时，同时引入根 `pubspec.yaml`（workspace）并启用 `resolution: workspace`。
- **执行结果**：根 `pubspec.yaml` 已建立，成员为 `app/mobile`、`packages/osn_protocol`、`packages/osn_identity`；统一使用根 `pubspec.lock`。未创建存储、传输、trust_view 空包。
- **理由**：空壳包会让 AI 与人类贡献者误判进度；workspace 的收益（统一解析、单一 lockfile）在第二个包出现时才成立。
- **代价**：Phase 0.1 的 CI 只覆盖一个目录；将来迁移时需要一次性调整（`pubspec.lock` 位置、IDE 配置）。
- **复审条件**：Phase 0.2 开始时执行迁移，并在 `CHANGELOG.md` 记录。

## ADR-012 技术栈：Flutter + Dart

- **状态**：已采纳
- **背景**：需要一个可维护、可测试、移动端 P2P 生态可用的技术栈。
- **选项**：(a) Flutter + Dart；(b) Kotlin 原生；(c) React Native；(d) Rust 核心 + 各端壳。
- **决定**：Flutter + Dart，业务核心为纯 Dart 包（不依赖 Flutter），便于 `dart test` 快速反馈与将来复用。
- **理由**：单一语言覆盖 UI 与协议逻辑；纯 Dart 包可以在 CI 里秒级跑完整业务测试；Flutter 的 Android 工具链成熟。
- **代价**：Dart 的 P2P 生态（`dart_libp2p`）年轻、单人维护，需要适配器隔离与锁版本。
- **复审条件**：Phase 2 若 Dart 侧传输方案全部不达标，评估"Rust 核心 + Flutter FFI"（此时 ADR 需重写）。

## ADR-013 信封签名覆盖 sender_id 与 sent_at

- **状态**：已采纳（Phase 0.2，2026-11-07）
- **背景**：PROTOCOL_SPEC 早期草案把签名范围写成 `payload`，但把 `sender_id`/`sent_at` 留在签名外，会让接收方可以替换发送方身份或声明时间而签名仍"有效"。
- **选项**：(a) 只签 payload；(b) 签 `{schema_version, type, sender_id, sent_at, payload}`；(c) 把 `signature` 也纳入签名。
- **决定**：(b)。签名字节 = `UTF-8("PeerServe:v1:" + JCS(signed_payload))`，`signature` 留在信封外层。
- **理由**：身份与时间是"谁在何时声明了什么"的组成部分；不签它们会让重放/替换攻击只改一个外层字段。签名覆盖签名自身则会产生递归，方案 (c) 不可行。
- **代价**：`sent_at` 被签名后不能由接收方"校正"；时间偏差只能在业务层容忍，不能改写信封。
- **复审条件**：若未来需要可转发的"时间戳证明"，应新增独立对象，而不是把 `sent_at` 移出签名范围。

## ADR-014 Agreement 双签使用两个独立信封

- **状态**：已采纳（Phase 0.2d，2026-11-07）
- **背景**：PROTOCOL_SPEC 7.3 草案把 `requester_signature` / `provider_signature` 列为 Agreement 字段；但本仓库已经规定签名放在信封外层，且信封签名覆盖 `sender_id`/`sent_at`。把签名塞进 payload 会产生"签名覆盖签名"的递归与重复校验。
- **选项**：(a) 在 Agreement payload 内嵌两个签名字段；(b) 双方各自对一个**相同 Agreement payload** 生成独立信封；(c) 只保留一个信封，另一方用单独确认事件。
- **决定**：(b)。需求方生成 `agreement.proposed` 信封，响应方生成 `agreement.signed` 信封；两个信封的 `payload` 必须规范化为相同字节。两个签名都验证通过才标记 `mutually_signed`。
- **理由**：复用统一信封校验与域分离；每个签名仍然绑定自己的 `sender_id`/`sent_at`；避免 payload 内签名递归。两个信封的 `sender_id`/`sent_at`/`type` 不同，因此**签名字节不同是正常的**，一致性检查应比较 `payload` 的 JCS，而不是整个信封。
- **代价**：一个"已签署协议"需要保存两个信封；导出时必须成对导出，否则只能证明单方签署。
- **复审条件**：若未来需要单文件、可离线转发的"双签证明"，可以定义独立的 `agreement.bundle` 对象，但不得把签名移进 payload 破坏现有信封规则。
